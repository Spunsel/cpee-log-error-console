LLM-Driven Process Modification

A user can request changes to a process in plain natural language. Because LLMs cannot reliably read or produce CPEE XML, the pipeline uses Mermaid flowchart syntax as an intermediate format — the process model is converted to Mermaid before being sent to the LLM, and the LLM's output is converted back to CPEE XML. Each user request produces one modification step; multiple requests produce a chronological sequence of steps.

Every modification step follows an identical five-stage pipeline. Understanding these stages is essential, because the debugging console displays all five for each step.

Stage 1 Input CPEE
→
CPEE → Mermaid
Stage 2 Input Mermaid
→
User request + LLM
Stage 3 User Input
→
LLM response
Stage 4 Output Mermaid
→
Mermaid → CPEE
Stage 5 Output CPEE

Event Logs — How Modifications Are Recorded

CPEE records every modification step in a structured event log. The log format used here is XES (eXtensible Event Stream), serialized as YAML — so each file has the extension .xes.yaml.

Markers Inside cpee:exposition

The exposition payload is plain text. Each of the five pipeline stages is delimited by a fixed marker string:

<!-- Input CPEE-Tree --> Stage 1 %% Input Intermediate Stage 2 # User Input: Stage 3 %% Output Intermediate Stage 4 <!-- Output CPEE-Tree --> Stage 5 # Used LLM: Optional

Typical Error Patterns to Watch For

Because the pipeline involves two format conversions and an LLM as an intermediary, errors can appear at multiple points:

LLM Syntax Errors

The LLM produces invalid Mermaid Syntax.

Structural Errors

Structural problems like reachability, soundness, boundedness.

Conversion Errors

During transformation between graph formats.
